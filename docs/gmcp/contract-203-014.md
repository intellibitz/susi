# GMCP-203-014 contract: Official Tasks extension and durable long-running work

Status: **contract pinned** (requirement `GMCP-203-014-01`, vector `VC-203-014`)
Baseline date: **2026-11-15**

This contract binds every normative clause of vector `VC-203-014` (`T-CODEXGMCPROADMAP-100`) and defines the complete architecture, compatibility boundaries, threat model, resource budgets, fixtures, and resolved design decisions required before implementing `T-CODEXGMCPROADMAP-101` through `T-CODEXGMCPROADMAP-106`. Every row in the behavior table is normative and pinned verbatim against `.agents/gmcp/requirements-ledger.json` and `.agents/gmcp/sources.json`.

## Normative clause

The shipped GMCP runtime across `crates/susi-gmcp/src/` and `crates/susi-wire-client/src/mcp.rs` must implement the Official MCP Tasks extension (`io.modelcontextprotocol/tasks`, `ext-tasks@2026-07-28`) across all **46** pinned normative clauses (`modern=41`, `optional=5`, `adapter=0`; `must=25`, `must_not=8`, `should=8`, `may=5`) and satisfy the `VC-203-014` vector mastery contract end-to-end on both server and client:

1. **Capability negotiation & server-directed task creation (`CreateTaskResult`)**:
   - Server advertises `capabilities.extensions["io.modelcontextprotocol/tasks"] = {}` in `server/discover` and `initialize` via `ExtensionRegistry::shipped()`.
   - Task creation is strictly server-directed per request (`EXT-TASKS-specification-2026-07-28-tasks-md-0059`, `-0061`). A server **MAY** return `CreateTaskResult` (`resultType: "task"`) for eligible `tools/call` requests only when the request includes `_meta["io.modelcontextprotocol/clientCapabilities"].extensions["io.modelcontextprotocol/tasks"]`, and **MUST NOT** infer task capability from earlier requests or return `CreateTaskResult` when absent.
   - If a server cannot fulfill a request without returning `CreateTaskResult` and the client omitted the extension capability on that request (or when servicing `tasks/get`, `tasks/update`, `tasks/cancel`, or `subscriptions/listen` with `taskIds` without the capability), it **MUST** return JSON-RPC `-32021` (`Missing required client capability`) with `data.requiredCapabilities.extensions["io.modelcontextprotocol/tasks"] = {}` (`-0063`, `-0457`, `-0798`, `-0799`).
   - `resultType: "task"` is reserved exclusively for `CreateTaskResult` (`-0102`); `tasks/get`, `tasks/update`, and `tasks/cancel` responses **MUST** set `resultType: "complete"` (`-0338`, `-0381`, `-0410`).
2. **Durable creation & process-restart survival (exactly-once settlement)**:
   - A server **MUST NOT** return `CreateTaskResult` until the new task record is durably persisted so an immediate `tasks/get` resolves cleanly without speculative polling retries (`-0300`).
   - Durable task state **MUST** survive server process restarts (`T-CODEXGMCPROADMAP-101`): persisted completed/failed/cancelled payloads remain retrievable until `ttlMs` expires without re-executing finished side effects, and interrupted non-terminal work settles deterministically once (never double-executing committed work or creating duplicate `taskId` records).
   - Pre-creation MRTR exchanges **SHOULD** resolve synchronously before returning `CreateTaskResult` (`-0302`).
3. **Explicit task state machine & terminal-state immutability**:
   - Canonical states (`TaskStatus`): non-terminal `{"working", "input_required"}` and terminal `{"completed", "failed", "cancelled"}`.
   - Permitted transitions only: `working -> input_required | completed | failed | cancelled`; `input_required -> working | completed | failed | cancelled`. Terminal states are strictly immutable: no background completion, `tasks/update`, `tasks/cancel`, or TTL sweep may overwrite a terminal payload once settled (`tasks/cancel` on a terminal task fails with `-32602`).
   - `tasks/get` returns `DetailedTask`: `working` / `cancelled` carry metadata only; `input_required` inlines all outstanding `inputRequests`; `completed` inlines `result` (including `CallToolResult` with `isError: true`); `failed` inlines JSON-RPC `error` + diagnostic `statusMessage` and **MUST** represent JSON-RPC protocol errors only, never `isError: true` tool results (`-0158`, `-0326`..`-0332`, `-0835`, `-0837`, `-0891`, `-0892`).
4. **Mid-flight MRTR (`tasks/update`, unique keys, trust boundary) & progress composition**:
   - `inputRequests` keys **MUST** be unique across the entire lifetime of a task (`used_input_keys`, `-0350`). Clients **MUST** apply full standalone elicitation/sampling/roots trust policy to `inputRequests` (`-0348`, `-0905`) and deduplicate keys across polls.
   - `tasks/update` accepts full or partial `inputResponses` for currently pending keys, ignores unknown, answered, or superseded keys cleanly (`-0379`), and acknowledges with `{}` (`UpdateTaskResult`, `resultType: "complete"`).
   - If the original request carried `_meta.progressToken`, progress notifications remain correlated to that token while the task is non-terminal and **MUST** stop immediately upon terminal settlement.
5. **Cooperative cancellation, TTL expiry, subscriptions (`notifications/tasks`), HTTP routing & client retries**:
   - Cancellation **MUST** use `tasks/cancel` (`CancelTaskResult` = `{}`, `resultType: "complete"`); `notifications/cancelled` **MUST NOT** cancel durable tasks (`-0385`, `-0404`, `-0410`).
   - Expired tasks (`createdAt + ttlMs` elapsed) may transition to `failed` or be purged; `tasks/get` on unknown or purged expired tasks **MUST** return `-32602` (`-0340`, `-0794`, `-0795`).
   - `subscriptions/listen` `notifications.taskIds` optionally pushes `DetailedTask` snapshots over `notifications/tasks`, after enforcing `-32021` capability checks and principal authorization before `notifications/subscriptions/acknowledged`; `notifications/progress` and `notifications/message` **MUST NOT** be sent on task subscription streams (`-0414`, `-0457`, `-0505`, `-0507`).
   - Streamable HTTP requests to `tasks/get`, `tasks/update`, and `tasks/cancel` **MUST** include `Mcp-Name: <params.taskId>` and `Mcp-Method` (`-0511`).
   - Clients (`crates/susi-wire-client/src/mcp.rs`) handle `CallToolResult` vs `CreateTaskResult`, reject unexpected `CreateTaskResult` on unsupported requests, persist task handles for resume, respect `pollIntervalMs`, treat `ttlMs` as a backstop, execute bounded transient transport retries without duplicating side effects, and track answered `inputRequests` keys (`-0308`, `-0310`, `-0346`, `-0377`, `-0408`).
6. **Unguessability & principal/authorization binding**:
   - Task IDs **MUST** be generated with cryptographic OS randomness (`uuid_v4()`, >= 122 bits entropy; `-0902`). Every `tasks/get`, `tasks/update`, `tasks/cancel`, and `subscriptions/listen.taskIds` request **MUST** authenticate and authorize the caller against the task's owning principal (`-0903`), rejecting cross-user, forged, or replayed handles fail-closed without exposing task existence (`-32602`; no `tasks/list` endpoint).

### Contract-mandated additions for `T-CODEXGMCPROADMAP-101..106` (target production-path invariants, not yet implemented)

- **Principal identity & ownership binding (`TaskPrincipal`, `OwnerKey` in `mcp/task_manager.rs`, `mcp/service.rs`, `mcp/http.rs`, `protocol.rs`)**: Capture canonical caller principal identity from the verified transport/authorization context (never forged client headers/params or bare session IDs) on task creation, and enforce constant-scope owner verification on `tasks/get`, `tasks/update`, `tasks/cancel`, and `subscriptions/listen.notifications.taskIds`, returning uniform `-32602` on unauthorized lookups.
- **Durable task store & restart reconciliation (`DurableTaskStore` under `susi_paths::SusiDirs::data_dir()` / `mcp/task_manager.rs`)**: Persist `TaskEntry` atomically + fsync *before* `spawn` returns `Task` (`CreateTaskResult` durability guarantee `-0300`), checkpoint transitions (`InputRequired`, `used_input_keys`, `Completed`, `Failed`, `Cancelled`, `run_epoch`, `ttlMs`), reload on process startup, serve settled terminal results within TTL, never re-run completed/cancelled tasks, and settle interrupted non-resumable in-flight tasks deterministically once (`Failed` with `-32603` unless explicitly resumable with idempotency fencing).
- **Wire gate & transport allowlisting (`crates/susi-gmcp/src/jsonrpc_gate.rs`, `crates/susi-gmcp/src/mcp/transport.rs`)**: Add `"tasks/get"`, `"tasks/update"`, `"tasks/cancel"` to `is_standard_method` and `"notifications/tasks"` to `is_standard_notification` so malformed no-id task messages fail closed (`-32600`) across stdio and HTTP instead of falling into foreign-notification ignore rules.
- **Push status subscriptions (`SubscriptionFilter.task_ids` in `mcp/model.rs`, `mcp/service.rs`, `protocol.rs`)**: Add optional `taskIds: Vec<String>` to `SubscriptionFilter`, validate capability (`-32021`), cap, and principal ownership before emitting `notifications/subscriptions/acknowledged`, deliver `notifications/tasks` with full `DetailedTask` snapshots on status changes, and enforce zero `notifications/progress` or `notifications/message` emissions on task subscription streams (`-0507`).
- **Rate-limiting, terminal hardening & input validation (`mcp/task_manager.rs`, `mcp/service.rs`)**: Add per-principal & global active-task caps, `pollIntervalMs` rate limiting on `tasks/get`, terminal-state checks on `tasks/update` (rejecting updates after terminal settlement), and explicit malformed/oversized `inputResponses` rejection while preserving spec-mandated ignore behavior for unknown/already-answered keys (`-0379`).
- **Client runtime & retries (`crates/susi-wire-client/src/mcp.rs` & `crates/susi-core/`)**: Expose opt-in `io.modelcontextprotocol/tasks` client capability flag, `CallToolOutcome` (`Complete | InputRequired | Task`), persisted task-handle polling loop respecting `pollIntervalMs` & `ttlMs` backstop, `Mcp-Name` HTTP header emission, `inputRequests` deduplication + answered-key tracking, `tasks/cancel`, unexpected `CreateTaskResult` rejection, and bounded transport-retry backoff without duplicate side effects.

## Compatibility and deprecation decisions

Ledger disposition tally for `VC-203-014` (`46` rows total): `modern=41`, `optional=5`, `adapter=0` (severity breakdown: `must=25`, `must_not=8`, `should=8`, `may=5`).

- **Canonical modern surface (`ext-tasks@2026-07-28`)**: The Tasks extension (`io.modelcontextprotocol/tasks`) is exclusively modern; zero rows carry `adapter` disposition. Servers advertise `capabilities.extensions["io.modelcontextprotocol/tasks"] = {}` and create tasks only when the individual request declares `io.modelcontextprotocol/clientCapabilities.extensions["io.modelcontextprotocol/tasks"]`, using `resultType: "task"` (`CreateTaskResult`), `tasks/get` (`DetailedTask` + `resultType: "complete"`), `tasks/update` (`inputResponses`), `tasks/cancel` (`{}` ack), `ttlMs`, `pollIntervalMs`, `subscriptions/listen.notifications.taskIds` (`notifications/tasks`), and HTTP `Mcp-Name`.
- **Excluded / deprecated `2025-11-25` draft task constructs (fail-closed)**:
  - **`tasks/list` removed (`-32601` Method not found)**: Intentionally omitted in `2026-07-28` (`EXT-TASKS-specification-2026-07-28-tasks-md-0904`) to eliminate cross-caller task enumeration and privacy leaks. Callers attempting `tasks/list` MUST receive `-32601`.
  - **`tasks/result` removed (`-32601` Method not found) & `_meta["io.modelcontextprotocol/related-task"]` retired**: Superseded by `tasks/get` inlining `result` or `error` on `DetailedTask` (`-0330`, `-0332`). Blocking `tasks/result` endpoints are NOT exposed.
  - **Client-initiated `params.task` augmentation & nested `CreateTaskResult.task` retired**: Task augmentation in `2026-07-28` is strictly server-directed (`-0059`, `-0260`), returning flat `Task` + `resultType: "task"`; clients cannot force task creation via `params.task`.
  - **`notifications/tasks/status` & legacy `ttl`/`pollInterval` field names retired**: Replaced by opt-in `subscriptions/listen` (`taskIds`) pushing `notifications/tasks`, and millisecond-suffixed `ttlMs` / `pollIntervalMs`.
  - **`notifications/cancelled` vs `tasks/cancel` separation**: `notifications/cancelled` applies solely to active JSON-RPC request streams (`subscriptions/listen`, synchronous `tools/call`), NEVER to spawned durable tasks (`-0385`).
- **Backwards-compatible fixed-shape client bridge**: `2025-11-25`-shaped fixed-return client helpers MAY internally execute `tasks/get` polling (when explicitly enabled for tasks) while preserving their synchronous return signature (`CallToolResult`), alongside full task-lifecycle APIs for modern hosts (`ext-tasks` Backwards Compatibility section).

## Threat model

| threat | attack / failure vector | contract mitigation |
|---|---|---|
| T1: Task ID enumeration or guessing (`-0902`) | Attacker guesses sequential/weak task IDs or calls `tasks/list` to hijack another caller's state or output | Mint task IDs via OS CSPRNG `uuid_v4()` (>= 122 random bits via `random_nonce_hex()`); reject `tasks/list` with `-32601`; return identical `-32602` error for missing, expired, or unauthorized task IDs |
| T2: Cross-user / cross-principal hijacking (`-0903`) | Authenticated caller B queries, updates, cancels, or subscribes to caller A's `taskId` via stolen handle or session swap | Bind `owner: TaskPrincipal` from verified transport auth identity on creation (never client-controlled parameters or bare session ID); verify `owner` on every `tasks/get`, `tasks/update`, `tasks/cancel`, and `subscriptions/listen.taskIds` |
| T3: Stale, expired, or forged handle / HTTP `Mcp-Name` mismatch (`-0340`, `-0511`) | Caller polls expired task past `ttlMs`, replays purged handle, or spoofs HTTP `Mcp-Name` routing header to hit wrong task shard | Sweep and enforce `ttlMs` before every read/update/cancel; validate HTTP `Mcp-Name == params.taskId` and `Mcp-Method` (`400` / `-32020` `HEADER_MISMATCH`); fail closed `-32602` on purged/missing tasks |
| T4: Replayed, duplicate, superseded, or untrusted `inputRequests`/`inputResponses` (`-0348`, `-0350`, `-0379`, `-0905`) | Malicious server reuses an `inputRequests` key to trick UX deduplication, malicious client replays answered key, or untrusted tool attempts high-trust escalation via `inputRequests` | Reject duplicate `inputRequests` keys in `TaskContext` (`used_input_keys`); `tasks/update` consumes currently pending keys atomically and ignores unknown/answered/superseded keys; enforce full `VC-203-013` elicitation/sampling/URL-consent trust checks on `inputRequests` |
| T5: Crash / restart double-execution & `CreateTaskResult` race (`-0300`) | Client polls before durable creation commits (`-32602` race), or server restart re-executes side-effectful task twice or drops terminal result | Persist task record atomically + fsync BEFORE returning `CreateTaskResult`; track `run_epoch` / idempotency fence in durable store so restarts never double-execute settled/committed work and deterministically fail orphaned non-resumable tasks (`-32603`) once |
| T6: Terminal-state mutation or cancellation race | Delayed tool completion or late `tasks/cancel` / `tasks/update` tries to overwrite settled `completed`, `failed`, or `cancelled` state | Guard all transitions with single-writer terminal immutability checks; refuse `tasks/cancel` and `tasks/update` on terminal tasks (`-32602`); enforce JSON-RPC protocol error (`failed` + `error`) vs tool error (`completed` + `isError: true`) split |
| T7: Unbounded task, polling, or notification DoS (`-0308`) | Client spawns unbounded tasks, polls in tight loops, floods `tasks/update`, or opens excessive task subscriptions | Enforce per-principal & global active task limits, retained terminal entry caps, `pollIntervalMs` rate limiting, `inputRequests` / payload bounds (`max_rpc_body_bytes`), and `MAX_ACTIVE_SUBSCRIPTIONS_PER_SESSION = 16` |
| T8: Capability spoofing, `resultType` forgery & covert stream leakage (`-0061`, `-0102`, `-0507`) | Server sends `CreateTaskResult` without per-request client capability, sets `resultType: "task"` on non-task response, or leaks logs/progress on `subscriptions/listen` | Require per-request `io.modelcontextprotocol/tasks` declaration (else `-32021`); validate `resultType == "task"` strictly on `CreateTaskResult` and `"complete"` on `tasks/{get,update,cancel}`; forbid `notifications/progress` and `notifications/message` on `subscriptions/listen` |

2. **Process-restart survival and "exactly-once" semantics**: Resolved via synchronous durable write *before* `CreateTaskResult` plus monotonic `run_epoch` / idempotency fencing: completed/cancelled/failed payloads are replayed immutably within `ttlMs` without re-invoking handlers, checkpointed resumable steps resume safely, and interrupted non-resumable background futures fail cleanly once (`-32603`) instead of double-executing side effects.

5. **Cancellation signal ownership**: Resolved per `-0385` & `-0404`: `tasks/cancel` cancels durable tasks cooperatively (`CancelTaskResult` ack `{}` with `resultType: "complete"`); `notifications/cancelled` only cancels active JSON-RPC requests and is ignored/never applied to durable tasks.
6. **Partial & stale `tasks/update` responses**: Resolved per `-0350` & `-0379`: `tasks/update` accepts partial subsets of currently pending keys (remaining `input_required`), deduplicates via atomic pending-map removal, rejects server key reuse via `used_input_keys`, and ignores unknown/answered/superseded keys cleanly.
7. **Elimination of `tasks/list` and `tasks/result`**: Resolved per `ext-tasks@2026-07-28` & `-0904`: neither `tasks/list` nor `tasks/result` exists on the modern wire (`-32601`); `tasks/get` (plus optional `notifications/tasks`) is the single retrieval surface.
8. **Principal isolation across transports**: Resolved per `-0903`: HTTP/gateway sessions derive `TaskPrincipal` strictly from verified authorization credentials (never client headers or bare session IDs); stdio uses its local OS-process principal; cross-principal requests return uniform `-32602` to prevent existence oracle leaks.
9. **Notification & progress composition**: Resolved per `-0507` & `VC-203-012`: `_meta.progressToken` remains active until terminal task transition on request progress notifications, while `notifications/progress` and `notifications/message` MUST NEVER be sent over `subscriptions/listen` task streams.
10. **HTTP routing headers**: Resolved per `-0511`: `Mcp-Method` and `Mcp-Name == params.taskId` are mandatory on Streamable HTTP `tasks/get`, `tasks/update`, and `tasks/cancel` requests.

### Incident triage

Treat any `verified: false` drift finding (`hash_drift` or `unfetchable`), cross-principal task leak, post-terminal state overwrite, plaintext token appearance in `tasks.json` or `PersistedTaskHandleStore`, `notifications/progress` or `notifications/message` leak onto `subscriptions/listen` task streams, silent startup over a corrupt `tasks.json`, or `stdout` non-JSON frame leak on zero `max_rpc_body_bytes` as a release-blocking incident. Preserve the `susi mcp ledger --drift` JSON report, `tasks.json` durable snapshot, HTTP/stdio JSON-RPC frames, server `stderr` diagnostics, and latest `.agents/gmcp/evidence/*.jsonl` proof records before remediation, then re-verify `gmcp_req_203_014`.

### Migration (schema evolution and upstream specification re-pinning)

1. **Client migration (`2025-11-25` -> `2026-07-28`)**: Legacy callers using synchronous `CallToolResult` signatures can adopt `Session::call_tool_resolving_tasks` as a zero-signature-change bridge while migrating to `Session::open_2026_07_28`, `call_tool_with_tasks`, `poll_task_until_done`, and `PersistedTaskHandleStore` (`version = 1`), retiring `params.task`, `tasks/list`, `tasks/result`, and `notifications/tasks/status`.
2. **Durable store schema evolution (`STORE_VERSION`)**: `tasks.json` embeds `STORE_VERSION = 1` as element `0` of `StoredState(u32, Vec<Stored>)` and writes atomically via `tasks.json.tmp.<pid>.<uuid>` + `sync_all()` + `rename()`. Any future format change increments `STORE_VERSION` with an explicit one-way reader for `STORE_VERSION - 1` while refusing unknown higher versions closed.
3. **Upstream specification re-pinning**: Update changed specification files under `.agents/gmcp/spec/` and SHA-256 digests in `.agents/gmcp/sources.json` alongside `.agents/gmcp/requirements-ledger.json` and `docs/gmcp/contract-203-014.md`, re-run `gmcp_req_203_014_01..06` and `check-gmcp-roadmap`, and append fresh `record-gmcp` proof records.

### Rollback

All contract prose (`docs/gmcp/contract-203-014.md`), `sources.json`, `requirements-ledger.json`, tests, and `.agents/gmcp/evidence/*.jsonl` chains are immutable, versioned Git artifacts. Server durable task snapshots (`tasks.json`, `STORE_VERSION = 1`) and client handle snapshots (`PersistedTaskHandleStore`, `version = 1`) update solely via atomic temp-file fsync + rename, so interrupted writes never corrupt the prior committed snapshot; rolling back a binary from a newer `STORE_VERSION` refuses startup cleanly (`unsupported task store version`) until the operator restores the prior `STORE_VERSION = 1` backup or clears transient expired state. After `git revert <commit>`, re-validate `~/.susi/config.json` (`susi_config::validate::validate_dir`), verify `susi mcp ledger --drift --refetched .agents/gmcp/spec` reports `verified: true`, re-run `gmcp_req_203_014_06_operations`, and append updated proof lines without deleting historical `.agents/gmcp/evidence/*.jsonl` entries.
